Exp 01:Create a Jira Task & Agile Lifecycle

Atlassian Jira Software (Web UI) • Agile Scrum Framework
Aim / Problem Statement
Primary Exam Problem: Create a Jira project named StudentProject. Add one task titled Complete Project Documentation and assign it to yourself.
Lab Manual Mapping (A27 Exp 1): Setting up an Agile Project Lifecycle in Jira — Epics, User Stories, and Sprint Planning.

Theory: Agile Lifecycle & Jira Management

Jira Software by Atlassian is an enterprise Agile project management platform that empowers DevOps teams to plan, track, release, and monitor software iteratively. Setting up an Agile project lifecycle establishes transparent workflows, backlog prioritization, and traceable sprint execution.

Key Agile Artifacts in Jira:

  • Project & Project Key: A central workspace grouping issues, boards, and workflows. Each project generates an uppercase identifier prefix (e.g. SP for StudentProject, SCRUM for Scrum projects).
  • Epic: A high-level initiative or large body of work that can be decomposed into smaller user stories (e.g. "Transport Management System").
  • User Story: A functional requirement written from an end-user persona perspective (e.g. "As a user, I want to register and login so that I can book vehicles").
  • Task: An independent technical unit of work to be performed (e.g. Complete Project Documentation).
  • Subtask: Granular technical work breakdown items nested beneath a user story or task (e.g. "Design Registration Page", "Implement User Authentication").
  • Product Backlog: Prioritized master repository of all pending stories, enhancements, and tasks.
  • Sprint: A fixed time-box (typically 1 to 2 weeks) during which the team commits to delivering a shippable increment.

Standard Agile Development Workflow:

To Do → In Progress → Code Review → Testing → Done

JQL (Jira Query Language) Quick Reference

JQL allows engineers to filter and locate specific work items across large enterprise projects. Use the Jira search bar or advanced issue search with these common filters:

Query 1: Filter all Tasks in project StudentProject:
project = "StudentProject" AND issuetype = Task
Query 2: Filter unstarted items assigned to the logged-in student:
assignee = currentUser() AND status = "To Do"
Query 3: Filter all issues currently active in open sprints:
Sprint in openSprints()

Step-by-Step UI Procedure

  1. Open your web browser and navigate to your Atlassian Jira site (e.g. https://your-domain.atlassian.net).
  2. In the top navigation menu, click Projects > Create project.
  3. Under Software Development, select the Kanban (or Scrum) template > click Use template.
  4. Select Team-managed (or Company-managed) project type.
  5. In the Name field, enter StudentProject. Notice that the Project Key automatically populates as SP. Click Create project.
  6. Click the global blue + Create button in the top navigation bar (or press shortcut key C).
  7. In the Create Issue modal window, enter the following details:
    • Project: Select StudentProject (SP)
    • Issue Type: Select Task
    • Summary: Type Complete Project Documentation
    • Description: Type Prepare software architecture specifications, lab manual, and deployment guidelines.
    • Assignee: Click Assign to me (your user avatar will be selected).
  8. Click Create to save the task.
  9. Navigate to the project Board or Backlog tab to verify the created issue.
Verification & Result Project StudentProject (SP) was successfully configured in Jira. Task SP-1 titled "Complete Project Documentation" is present in the TO DO column, assigned to self with verified issue details.

Viva-Voce Q&A
Q1: What is the hierarchy between Epics, User Stories, and Tasks in Jira?
An Epic is a high-level strategic initiative. It is broken down into User Stories (end-user requirements). User Stories and Tasks are further subdivided into technical Subtasks for individual engineers.
Q2: What is the purpose of the Project Key in Jira?
The key forms the unique prefix for all issue identifiers (e.g. SP-1, SP-2) to reference issues across Git commits, pull requests, CI/CD pipelines, and boards.
Q3: What is JQL (Jira Query Language) used for?
JQL is a powerful SQL-like syntax used to construct custom filters, search issues by project/status/assignee, and populate automated dashboard widgets and boards.

The Assignee is the engineer actively responsible for executing the work item; the Reporter is the author or team member who logged the issue.

Exp 02:Track Task Progress & Sprint Monitoring

Atlassian Jira Software (Web UI) • Burndown & Velocity Reports
Aim / Problem Statement
Primary Exam Problem: In Jira, create a Jira task titled Testing Activity. Change its status from To Do to In Progress and then Done. Display the completed task.
Lab Manual Mapping (A27 Exp 2): Tracking Sprint Progress using Burndown and Velocity Charts in Jira.

Theory: Workflow Tracking & Sprint Metrics

A Jira Workflow represents the sequence of statuses and transitions that an issue travels through during its lifecycle from backlog creation to final resolution. In Scrum, monitoring progress during a sprint ensures that bottlenecks are identified early and delivery commitments are met.

Workflow Status Lifecycle:

  • To Do: Work item is specified and prioritized, but active development or testing has not yet commenced.
  • In Progress: Active effort is underway by the assignee.
  • In Review / Testing: Code or deliverables are being peer-reviewed, tested, and validated against acceptance criteria.
  • Done: All acceptance criteria and Definition of Done (DoD) requirements are satisfied. The task is closed.

Sprint Monitoring Reports in Jira:

  • Sprint Burndown Chart: Visualizes the remaining effort over the duration of an active sprint. The horizontal axis represents sprint calendar dates; the vertical axis represents remaining effort (Story Points or issue count). As tasks move to Done, the line burns down toward zero.
  • Velocity Chart: Displays the amount of work committed vs work completed across consecutive sprints. It measures the team's historical delivery capacity to improve future sprint planning.
  • Story Points: An abstract estimation unit (often based on the Fibonacci sequence: 1, 2, 3, 5, 8, 13) reflecting relative effort, complexity, and technical risk.

Scrum Iteration Workflow:

Product Backlog → Sprint Planning → Sprint Backlog → Active Sprint → Daily Scrum → Burndown Monitoring → Velocity Analysis → Sprint Review → Sprint Retrospective

Step-by-Step UI Procedure

  1. In project StudentProject, click the + Create button in the top navigation bar.
  2. Set Issue Type to Task, enter Summary: Testing Activity, set Assignee: Assign to me, and click Create. The task appears as SP-2 in the TO DO column.
  3. Transition to In Progress: Drag the card Testing Activity from the TO DO column into the IN PROGRESS column (or open the card modal and select In Progress from the status dropdown).
  4. Transition to Done: Drag the card from IN PROGRESS into the DONE column (or change status dropdown to Done).
  5. Display Completed Task Details: Click on task SP-2 to open its details view:
    • Confirm the status displays as DONE with a green checkmark badge.
    • Scroll to the Activity > History tab to inspect the timestamped transition audit trail: To Do → In Progress followed by In Progress → Done.
  6. Access Agile Reports (Burndown & Velocity):
    • In the left sidebar, click Reports.
    • Select Burndown Chart: Inspect the guideline vs actual remaining work curve for the sprint.
    • Select Velocity Report: View the comparative bar chart of committed vs completed Story Points across sprints.
Verification & Result Task SP-2 (Testing Activity) was successfully transitioned through the complete workflow lifecycle to DONE status with full historical audit logging. The Sprint Burndown and Velocity reports were accessed and evaluated.

Viva-Voce Q&A
Q1: What is a Jira workflow transition?
A transition is a directed link that enables an issue to move from one status to another (e.g. from To Do to In Progress) governed by project permissions and validation rules.
Q2: What does a horizontal flat line or an upward spike on a Burndown Chart indicate?
A flat line indicates work has stalled or tasks are blocked. An upward spike indicates scope creep—new tasks or story points were added to the sprint after it started.
Q3: What is Team Velocity and how does it help in Sprint Planning?
Velocity is the average number of Story Points a team completes per sprint. It allows teams to realistically forecast and commit to future sprint workloads based on historical data.
Q4: What is Definition of Done (DoD)?
A formalized checklist of quality criteria (such as code reviewed, unit tests passing, documentation updated, and deployed to staging) required before declaring an issue completed.

Exp 03:Perform Git Branch and Merge

VS Code + Git Terminal • Version Control
Aim / Problem Statement
Primary Exam Problem: Create a Git repository. Create a branch named feature, add a file named student.txt, commit the file, and merge the branch into main.
Lab Manual Mapping (A27 Exp 3): Version Control with Git — Branching, Merging, and Resolving Conflicts.

Theory: Git Architecture & Branching

Git is an industry-standard distributed version control system (DVCS) that snapshots project states across time. Branching creates lightweight, independent lines of development allowing engineers to build features in isolation without disrupting the stable main codebase.

Fundamental Git Operations:

  • Repository (git init): The .git database storing full commit history, object trees, and branch references.
  • Working Tree & Staging Area (git status, git add): The three-tier architecture separates uncommitted working files, staged changes ready for snapshotting (index), and committed history.
  • Commit (git commit): A cryptographically hashed (SHA-1) immutable snapshot of all staged files with author, timestamp, and message.
  • Branch (git branch / git switch): A movable 41-byte pointer referencing a specific commit. Moving between branches switches the working tree files instantly.
  • Fast-Forward Merge: When the target branch (main) has no divergent commits compared to the feature branch, Git simply advances the main pointer forward to match the feature tip without generating a separate merge commit.
  • Log & History (git log): Traverses commit ancestry to audit project evolution.

Step-by-Step Procedure & Individual Commands

Step 1: In VS Code, open an empty project folder (e.g. C:\DevOpsPractical\exp3_git via File > Open Folder...). Open the integrated terminal (Ctrl + `) and initialize Git with default branch main:
git init -b main
Step 2: Configure your Git user identity (if not already set globally):
git config user.name "Student"
git config user.email "student@exam.local"
Step 3: In VS Code, create a file named README.txt with title text, then stage and make the initial commit on main:
git add README.txt
git commit -m "Initial commit on main"
Step 4: Create and switch to the new branch named feature (using modern git switch -c or classic git checkout -b):
git checkout -b feature
(Modern Git switch alternative):
git switch -c feature
Step 5: In VS Code Explorer, click New File, name it student.txt, and write your details:
student.txt (in VS Code Editor) 
Student Name: DevOps Practical Candidate
Roll Number: 20
Subject: DevOps Lab Practical
Step 6: Check working tree status and stage the newly created student.txt file in terminal:
git status
git add student.txt
Step 7: Commit the file on the feature branch:
git commit -m "Add student.txt on feature branch"
Step 8: Switch back to the main branch:
git checkout main
Step 9: Merge the feature branch into main (executes fast-forward merge):
git merge feature
Step 10: Verify that student.txt is present and inspect the visual commit graph:
git log --oneline --graph --all

Viva-Voce Q&A
Q1: What does git checkout -b feature (or git switch -c feature) do?
It creates the new branch named 'feature' from the current HEAD commit and immediately switches your active working tree to that branch.
Q2: What is a Fast-Forward merge?
A merge where Git simply advances the target branch pointer directly to the tip of the feature branch because there are no conflicting or divergent commits on the target branch.
Q3: What is the difference between git switch and git checkout?
git checkout was overloaded to handle both branch switching and file restoration. Git 2.23+ introduced git switch exclusively for branches and git restore for files.
Q4: What is the difference between working directory, staging area, and local repository?
Working directory holds untracked/modified local files; staging area (index) holds files prepped for commit; local repository (.git) stores permanently recorded commit snapshots.

Exp 04:Resolve Git Merge Conflict

VS Code + Git Terminal • Conflict Resolution
Aim / Problem Statement
Primary Exam Problem: Create a Git repository. Modify the same line of a file in two branches. Merge the branches and resolve the conflict.
Lab Manual Mapping (A27 Exp 3 - Part 2): Creating and Resolving Merge Conflicts in Git with Visual Studio Code.

Theory: Merge Conflicts & Conflict Markers

A Merge Conflict occurs when Git cannot automatically reconcile concurrent changes—specifically when two branches modify the exact same line in a file with differing text. Git halts the merge, preserves both variants inside the file surrounded by special Conflict Markers, and leaves the resolution to the developer.

Understanding Conflict Marker Anatomy:

  • <<<<<<< HEAD : Designates the beginning of the conflicting block from the branch you currently have checked out (e.g. main).
  • ======= : The visual divider separating the two competing sets of changes.
  • >>>>>>> feature-branch : Designates the end of the conflicting block from the incoming branch being merged.

VS Code Visual Merge Editor:

Visual Studio Code natively parses conflict markers and displays clickable action codelenses directly above each conflict block: Accept Current Change, Accept Incoming Change, Accept Both Changes, or Compare Changes.

Step-by-Step Procedure & Individual Commands

Step 1: In VS Code, open an empty folder (e.g. C:\DevOpsPractical\exp4_conflict). In terminal (Ctrl + `), initialize Git:
git init -b main
Step 2: In VS Code, create a file named config.txt with content: App Version 1.0 (Original). Stage and commit on main:
git add config.txt
git commit -m "Base commit with config.txt"
Step 3: Create and switch to a branch named feature-branch:
git checkout -b feature-branch
Step 4: In VS Code editor, open config.txt, modify line 1 to App Version 2.0 (Modified by Feature), save (Ctrl + S), and commit:
git commit -am "Update config on feature branch"
Step 5: Switch back to the main branch:
git checkout main
Step 6: In VS Code editor, open config.txt and modify the exact same line 1 to App Version 2.0 (Modified by Main), save (Ctrl + S), and commit:
git commit -am "Update config on main branch"
Step 7: Attempt to merge feature-branch into main (Git detects competing edits and generates a merge conflict):
git merge feature-branch
Step 8: In VS Code editor, open config.txt. Notice the conflict markers. Click Accept Incoming Change or edit manually to produce the unified resolution:
config.txt (Resolved in VS Code Editor) 
App Version 2.0 (Unified Resolution)

Ensure all conflict marker lines (<<<<<<<, =======, >>>>>>>) are deleted, then save (Ctrl + S).

Step 9: Stage the resolved file in terminal:
git add config.txt
Step 10: Finalize and commit the merge resolution:
git commit -m "Resolved merge conflict between main and feature-branch"
Step 11: Verify clean working tree status and inspect the merged commit graph:
git status
git log --oneline --graph
VS Code Terminal Output (Conflict & Resolution)
C:\DevOpsPractical\exp4_conflict> git merge feature-branch Auto-merging config.txt CONFLICT (content): Merge conflict in config.txt Automatic merge failed; fix conflicts and then commit the result. C:\DevOpsPractical\exp4_conflict> git commit -m "Resolved merge conflict between main and feature-branch" [main d7381b2] Resolved merge conflict between main and feature-branch C:\DevOpsPractical\exp4_conflict> git status On branch main nothing to commit, working tree clean
Verification & Result Conflicting changes were intentionally introduced on the same line across main and feature-branch. Git successfully generated conflict markers, which were resolved cleanly in VS Code. Staging and committing produced a resolved merge commit, returning the repository to a clean working state.

Lab Manual Mapping (A27 Exp 4): Implementing Git Flow and Collaborative Workflows using GitHub.

Theory: Git Flow & GitHub Collaborative Workflows

GitHub provides remote cloud hosting for Git repositories, enabling distributed team collaboration, code reviews, and automated CI/CD pipelines.

Git Flow Branching Strategy:

  • main branch: Contains strictly stable, production-ready, release-tagged code.
  • develop branch: Central integration branch where all feature deliverables combine before release.
  • feature/* branches: Dedicated branches where individual developers build isolated capabilities (e.g. feature-login, feature-registration, feature-events) without disrupting teammates.
  • release/* & hotfix/* branches: Used to prepare releases or patch urgent production bugs.

Collaborative Team Workflow Lifecycle:

Clone Remote → Checkout Feature Branch → Commit Changes → Push Feature Branch → Open Pull Request (PR) → Peer Code Review → Merge to Main → Pull Latest Main Locally

Viva-Voce Q&A
Q1: What does the -u flag do in git push -u origin feature?
It sets upstream tracking references, associating the local feature branch with origin/feature so subsequent git push or git pull commands do not require specifying remote and branch names.
Q2: How do you authenticate Git with GitHub from Windows?
Using Git Credential Manager (GCM) for Windows via browser OAuth login or a GitHub Personal Access Token (PAT).

Git Flow isolates unstable feature development on separate branches, preventing untested code from polluting the production main branch until peer-reviewed and tested.

To synchronize their local main with recent changes merged by teammates, preventing future merge conflicts when branching.

Exp 06:Execute a Jenkins Pipeline & Automated CI/CD

Jenkins CI/CD Automation • GitHub Webhooks
Aim / Problem Statement
Primary Exam Problem: Create a Jenkins pipeline that prints Welcome to DevOps Practical and Build Successful in the console output.
Lab Manual Mapping (A27 Exp 5): Building an Automated CI/CD Pipeline using Jenkins and GitHub Webhooks.

Theory: Continuous Integration & Continuous Deployment (CI/CD)

CI/CD automates the traditional manual development cycle (writing code → manual testing → manual uploading → manual deployment).

  • Continuous Integration (CI): Automatically fetches code, compiles, and runs automated unit/integration tests on every commit pushed to GitHub, ensuring code quality and catching bugs early.
  • Continuous Delivery (CD): Automatically packages tested builds into release-ready artifacts (e.g. Docker images, binaries, packages).
  • Continuous Deployment (CD): Automatically publishes verified packages directly to production servers with zero manual intervention.

Jenkins Automation Server & GitHub Webhooks:

  • Jenkins: An open-source automation server acting as an automated assistant monitoring code repositories. When triggers occur, Jenkins clones the repo, executes build scripts, runs tests, and generates reports.
  • GitHub Webhook: An instantaneous event-driven HTTP push notification. Instead of Jenkins polling GitHub continuously ("Any new code?"), GitHub proactively notifies Jenkins ("New commit received!") via http://<jenkins-ip>:8080/github-webhook/.

Complete CI/CD Pipeline Lifecycle:

Developer Git Push → GitHub Webhook → Jenkins Trigger → Clone Repository → Build Stage → Test Stage → Green Success

Pipeline Code (Jenkinsfile)

Jenkinsfile (Declarative Pipeline) 
pipeline {
    agent any

    stages {
        stage('Welcome Stage') {
            steps {
                echo 'Welcome to DevOps Practical'
            }
        }

        stage('Build Stage') {
            steps {
                echo 'Compiling application...'
                echo 'Build Successful'
            }
        }
    }

    post {
        success {
            echo 'Pipeline Completed With Result: SUCCESS'
        }
    }
}

Step-by-Step UI Procedure

  1. Open your browser at http://localhost:8080 and log in to Jenkins.
  2. Click New Item on the left dashboard menu.
  3. Enter item name: DevOps_Exam_Pipeline, select Pipeline, and click OK.
  4. Scroll to the Pipeline configuration section > set Definition to Pipeline script.
  5. Paste the Declarative Pipeline script above into the script editor.
  6. Under Build Triggers, check GitHub hook trigger for GITScm polling (or check Poll SCM with schedule * * * * *).
  7. Click Save.
  8. Click Build Now from the left sidebar to execute build #1.
  9. Click #1 under Build History > select Console Output. Verify both required output strings appear: Welcome to DevOps Practical and Build Successful.

Automated Webhook Trigger using Localtunnel (Zero Signup / Zero Token)

Because GitHub is hosted on the public cloud, it cannot directly reach http://localhost:8080 on your local computer. Use localtunnel to expose Jenkins publicly with zero configuration:

Step 1: In your Command Prompt or PowerShell, start a public tunnel to Jenkins port 8080:
npx localtunnel --port 8080
Localtunnel will output your unique public URL (e.g. your url is: https://plenty-rules-jog.loca.lt).
Append /github-webhook/ to form your GitHub Webhook Payload URL:
https://<your-subdomain>.loca.lt/github-webhook/
Step 2 (Add Webhook in GitHub):
  1. In your GitHub repository, navigate to Settings > Webhooks > Add webhook.
  2. Payload URL: Paste https://<your-subdomain>.loca.lt/github-webhook/ (keep the trailing slash /).
  3. Content type: Select application/json.
  4. Which events would you like to trigger this webhook?: Select Just the push event.
  5. Click Add webhook. Keep your localtunnel terminal window running during testing.

Exp 07:Build a Docker Image

Docker Desktop + VS Code (Windows) • Containerization
Aim / Problem Statement
Primary Exam Problem: Create a Dockerfile for a simple HTML page displaying Welcome to Docker. Build the image and run it in a container.
Lab Manual Mapping (A27 Exp 6): Containerizing Applications using Docker — Creating Dockerfiles and Running Containers.

Theory: Docker Containerization Architecture

Docker solves the classic "It works on my machine!" software deployment failure by packaging application code along with all system runtimes, libraries, and environment dependencies into a portable, lightweight container.

Core Docker Architecture & Analogies:

  • Docker Image (Recipe / Blueprint): An immutable, read-only static template specifying OS layers and application code.
  • Docker Container (Cooked Food / Running Instance): A live, running process isolated by Linux namespaces and cgroups. Multiple containers can run from a single image.
  • Docker Client & Engine: The CLI client (docker build, docker run) sends API requests to the Docker Engine daemon executing via WSL2 on Windows.
  • Dockerfile Instructions:
    • FROM : Specifies base operating environment (e.g. nginx:alpine).
    • COPY : Transfers local files into container filesystem.
    • EXPOSE : Declares listening ports.
    • CMD vs RUN : RUN executes during image creation to install libraries; CMD executes when the container launches.

Theory: Kubernetes Container Orchestration Architecture

Kubernetes (K8s) is an enterprise open-source container orchestration engine that automates the deployment, scaling, load balancing, and self-healing management of containerized applications across host clusters.

Key Kubernetes Architectural Concepts:

  • Pod: The fundamental, smallest deployable compute unit in Kubernetes. A Pod encapsulates one or more shared containers, storage volumes, and network IPs.
  • Node (Master vs Worker): Worker nodes run container workloads; the Control Plane (Master) schedules pods, maintains cluster state, and monitors node health.
  • Deployment & ReplicaSet: A declarative controller that manages application rollouts and ensures the desired number of Pod replicas (e.g. replicas: 3) are running continuously. If a pod crashes, Kubernetes automatically spins up a replacement pod (self-healing).
  • Scaling: Increasing or decreasing the number of Pod replicas horizontally using kubectl scale or declaring replicas: N in YAML.

Prerequisite: Kubernetes in Docker Desktop

In Docker Desktop, click the Settings gear icon > select Kubernetes > check Enable Kubernetes > click Apply & restart. Ensure the Kubernetes indicator in the bottom-left turns green.

    # Step 1: Open Google

    # Step 5: Close browser session cleanly

Theory: Observability, Prometheus & Grafana Dashboards

Observability provides deep real-time visibility into the health and performance of distributed systems across three pillars: Metrics (numeric time-series telemetry), Logs (discrete timestamped events), and Traces (request path journeys).

Monitoring Architecture:

  • Prometheus: A time-series database and monitoring server that pulls (scrapes) numeric metrics over HTTP at scheduled intervals and stores them with timestamped key-value tags.

  • PromQL (Prometheus Query Language): Used to calculate real-time usage percentages:
    • CPU Utilization: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100)
    • Memory Consumption: (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100

Viva-Voce Q&A
Q1: What are the three pillars of system observability?
Metrics (numeric telemetry over time), Logs (timestamped event records), and Traces (end-to-end request journeys across distributed microservices).
Q2: What is the difference between Prometheus and Grafana?
Prometheus acts as the time-series metric collector and storage engine; Grafana acts as the visualization layer that connects to Prometheus to render interactive dashboards.
Q3: What is PromQL and what does the rate() function calculate?
PromQL is Prometheus Query Language. The rate() function calculates the per-second average rate of increase of a time series counter over a specified time window.
Q4: How do threshold colors help in Grafana dashboards?
Thresholds visually highlight operational health: Green indicates normal operating levels, Yellow warns of elevated utilization, and Red flags critical bottlenecks requiring intervention.
Q5: What is Node Exporter in Prometheus monitoring?
Node Exporter is a lightweight Prometheus exporter that exposes machine-level hardware and OS metrics (CPU, RAM, disk, network) over an HTTP endpoint for scraping.
